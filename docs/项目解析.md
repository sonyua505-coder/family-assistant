# 第 0 章 前置知识：把地基打牢

## 0.1 Node.js 到底是什么，它怎么工作

你可能听过"JavaScript 是浏览器里的脚本语言"。**Node.js 把 JavaScript 搬到了服务器上**——它基于 Chrome 浏览器的 V8 引擎，让 JS 代码可以读写文件、监听网络端口、访问数据库，就像 Python/Java 一样做后端。

但它和 Python/Java 有一个**根本性差异：执行模型**。

- Python/Java（多线程阻塞式）：一个请求来了，操作系统给它分配一个线程，线程等着 I/O（读数据库、读文件、等网络）完成，期间这个线程就"干等"着。并发量靠"线程数"扛，线程很贵（内存）。
- Node.js（单线程事件驱动）：**整个进程只有一个主线程**。它不"干等" I/O——发出去一个 I/O 请求后，立刻去做下一件事；I/O 完成时，操作系统通知 Node，Node 把对应的回调函数放进"事件队列"，主线程处理完当前任务后取出执行。

这个模型叫**事件循环（Event Loop）**，伪代码大概是：

```
while (true) {
  处理微任务队列里的所有任务;
  从宏任务队列取出一个任务执行;
  检查是否有完成的 I/O 回调，有就执行;
}
```

**关键推论**：在 Node 里，"耗时"的操作必须是非阻塞的（异步），否则一个慢查询会卡死整个服务器（因为只有一条线程）。这也是为什么本项目选 better-sqlite3 时做了特别权衡——见 §3.2。

**npm（Node Package Manager）**：Node 的包管理器，相当于 Python 的 pip、Java 的 Maven。`package.json` 是项目的"清单"（依赖、脚本、元信息），`npm install` 按它下载依赖到 `node_modules/`。

## 0.2 TypeScript：带类型的 JavaScript

TypeScript（TS）是 JavaScript 的超集——**在 JS 语法之上加了类型系统**。浏览器和 Node 都不能直接运行 TS，需要编译器 `tsc` 把它转成纯 JS（这个过程叫**编译/转译 transpile**）。

```ts
// TypeScript
interface Bill {
  id: number;
  amount: number;      // 单位：分
  category: string;
}

function total(bills: Bill[]): number {
  return bills.reduce((s, b) => s + b.amount, 0);
}

const n: number = total([{ id: 1, amount: 100, category: '餐饮' }]);
// 编译后（dist 里的 .js）：
// function total(bills) { return bills.reduce((s, b) => s + b.amount, 0); }
```

类型在**编译期**检查（写错了编译就报错），运行时不产生任何东西——`interface`、`: number` 这些全被擦除。所以 TS 是"开发期的安全网"，不是运行期的东西。

本项目几个必懂的类型写法：

| 写法 | 含义 |
|---|---|
| `x: number \| undefined` | 联合类型：x 可能是 number，也可能是 undefined |
| `x!` | 非空断言："我保证 x 这里不是 null/undefined"（编译期用的，运行期不检查） |
| `T | undefined` 的 `?.` | 可选链：`a?.b` 表示 a 为 null/undefined 时整个表达式为 undefined，不报错 |
| `as T` | 类型断言：告诉编译器"请把它当成 T"（运行时无操作） |
| `Array<T>` / `T[]` | 泛型数组 |
| `Map<K, V>` / `Set<T>` | 泛型容器 |
| `interface X { ... }` | 结构类型（鸭子类型：长得一样就兼容） |
| `import ... from '...'` | ESM 模块导入（§0.3） |

## 0.3 模块系统：ESM（ECMAScript Modules）

早期 JS 没有模块概念，后来社区发明了 CommonJS（`require`），再后来官方标准 ESM（`import/export`）。本项目 `package.json` 里 `"type": "module"`，即全程用 **ESM**：

```ts
// 导出（src/modules/bills/bills.ts）
export function createBill(...) { ... }
export const BILL_CATEGORIES = [...];

// 导入（src/modules/bills/routes.ts）
import { createBill, BILL_CATEGORIES } from './bills.js';   // 注意：NodeNext 下要写 .js 后缀！
```

> 坑点：TS 的 `moduleResolution: NodeNext` 要求**相对导入必须带 `.js` 后缀**（即使源文件是 `.ts`）。这是 Node ESM 的硬性规定，新人最容易在这里报 `ERR_MODULE_NOT_FOUND`。

## 0.4 SQLite：嵌入式关系数据库

SQLite 不是"数据库服务器"，而是一个**C 语言库**，直接把数据库存在一个文件里。没有独立的进程、没有端口、不需要用户名密码。你的程序链接它，它帮你管理文件内的表/索引/事务。对比：

| | SQLite | MySQL/PostgreSQL |
|---|---|---|
| 形态 | 库文件 | 独立服务进程 |
| 连接 | 直接函数调用 | 网络连接（TCP） |
| 适用 | 单机、低并发、嵌入式 | 多客户端、高并发 |
| 并发 | 单写多读（WAL 缓解） | 成熟的多写并发 |

对"家庭单用户"规模，SQLite 是近乎完美的选择：零运维、备份就是拷文件。

## 0.5 HTTP 快速回顾（后面会反复用）

- **方法**：GET（读）、POST（创建）、PATCH（部分更新）、DELETE（删除）。
- **状态码**：2xx 成功、4xx 客户端错（400 参数错 / 401 未认证 / 403 无权限 / 404 不存在 / 409 冲突 / 429 限流）、5xx 服务器错。
- **请求头**：`Authorization`（凭证）、`Content-Type`（body 格式：`application/json` / `application/x-www-form-urlencoded`）。
- **无状态**：HTTP 自己不记得"上次是谁"，所以每次请求都要带凭证（令牌/key/身份头）。

## 1.2 装依赖，认识 Fastify

```bash
npm install fastify
npm install -D typescript tsx @types/node
```

**Fastify 是什么**：Node 生态的 Web 框架（类似 Flask/Spring Boot 之于 Python/Java）。它帮你做：路由匹配、请求解析（query/params/body/headers）、响应序列化、中间件式钩子、错误处理、日志。核心概念：

```
Fastify 实例（app）
 ├─ app.get('/path', { options }, handler)     ← 注册路由
 ├─ options.preHandler: [钩子1, 钩子2]          ← 请求进 handler 前依次执行（鉴权/校验）
 ├─ app.register(pluginFn, deps)               ← 插件化组织模块
 ├─ app.setErrorHandler(fn)                    ← 全局错误处理
 └─ app.listen({ port })                       ← 监听端口
```

**Fastify 请求生命周期（理解它=理解一半项目）**：

```
收到请求
 → 解析 URL/body/query
 → 按路径匹配路由
 → 依次执行 preHandler 钩子（任何一个可提前返回=拦截请求）
 → 进入路由 handler（业务代码）
 → handler 返回 → 序列化成响应 → 发送
 → 若 handler 抛错 → setErrorHandler 统一兜底
```

本项目大量使用 `preHandler` 做鉴权（§5）和令牌校验（§12），这就是"中间件"的 Fastify 叫法。

## 1.3 写第一个路由并运行

最小的 Fastify 服务（对应本项目 src/app.ts 的雏形）：

```ts
import Fastify from 'fastify';

const app = Fastify();

app.get('/hello', async () => ({ ok: true, msg: '你好' }));
//          ↑ 路由路径    ↑ handler：async 函数，返回值自动 JSON 序列化

app.listen({ port: 3000, host: '0.0.0.0' });
```

```bash
npx tsx hello.ts        # 用 tsx 直接跑
curl http://127.0.0.1:3000/hello
# → {"ok":true,"msg":"你好"}
```

**为什么 handler 是 async 函数**：Fastify 的 handler 可以是异步的，内部 await 数据库/网络后返回即可，框架负责把 Promise 的结果序列化出去。async/await 是 JS 处理异步的标准写法（本质是 Promise 的语法糖）。

# 第 2 章 配置系统

## 2.1 为什么要有配置层

硬编码路径/密钥/端口是坏味道：换环境（本地/云端）就得改代码。标准做法是**环境变量**——代码从环境读配置，不同环境用不同 `.env` 文件注入。

**dotenv** 做的事：读项目根目录的 `.env` 文件，把里面的 `KEY=VALUE` 加载进 `process.env`（Node 进程的环境变量字典）。

## 2.2 config.ts 逐行解析

```ts
// src/config.ts —— 整个文件就一件事：把环境变量变成类型安全的 Config 对象
export interface Config {          // 声明配置的形状（类型安全的关键）
  apiPort: number;                 // API 端口
  webPort: number;                 // Web 端口（预留）
  dbPath: string;                  // SQLite 文件路径
  apiKey: string;                  // 插件调用密钥
  adminKey: string;                // 内部管理密钥
  tz: string;                      // 调度器时区
  ztIp: string;                    // ZeroTier 内网 IP（云端）
  publicWebBase: string;           // 铸造 Web 链接用的基础 URL
  logLevel: string;
  schedulerEnabled: boolean;       // 是否启动调度器
  backupDir: string;               // 冷备目录
}

export function loadConfig(env: NodeJS.ProcessEnv = process.env): Config {
  const cfg: Config = {
    apiPort: toInt(env.API_PORT, 3000),              // 读环境变量，缺省 3000
    dbPath: env.DB_PATH ?? './data/dev.db',
    apiKey: env.X_API_KEY ?? '',
    // ...
    schedulerEnabled: env.SCHEDULER_ENABLED !== 'false',  // 只有显式 false 才关
  };
  if (!cfg.apiKey) throw new Error('缺少 X_API_KEY（.env）');  // 关键配置缺失=拒绝启动
  if (!cfg.adminKey) throw new Error('缺少 ADMIN_KEY（.env）');
  return cfg;
}

function toInt(v: string | undefined, fallback: number): number {
  const n = Number(v);
  return Number.isFinite(n) ? n : fallback;   // 非法数字回退默认值
}
```

教学点：

- **`NodeJS.ProcessEnv`** 是 Node 给 `process.env` 声明的类型（`Record<string, string | undefined>`）。
- 所有配置**归一成 typed 对象**后向下传递——业务代码永远不直接读 `process.env`，改配置影响面小、可测。
- `??` 是"空值合并"运算符：左边是 `null/undefined` 才取右边（`||` 会把空串/0 也替换掉，这里用 `??` 更精确）。
- `.env` 在 `.gitignore` 里（密钥不提交），云端用 `deploy/env.example` 模板复制成服务器上的 `.env`。

# 第 3 章 接上数据库

## 3.1 better-sqlite3：为什么是"同步"的

回到 §0.1 的结论：Node 单线程，异步 I/O 是王道。**但 SQLite 是例外**——它是本地文件库，读写在微秒~毫秒级，而且 better-sqlite3 特意做成**同步 API**：

```ts
// 异步风格（MySQL 驱动等）
const rows = await db.query('SELECT ...');   // 要 await，写起来绕

// better-sqlite3 风格（本项目）
const row = db.prepare('SELECT ...').get(id);  // 直接返回结果！
```

同步的好处（对本项目是决定性优势）：

1. **没有回调地狱**：逻辑是线性的，`if (row)` 后面直接能用，不用 `.then()`。
2. **没有并发交叉**：JS 单线程 + 同步执行 = 同一时刻只有一段代码在碰数据库，天然没有"两个请求交叉写坏数据"的问题。
3. **事务简单**：一个同步函数包住就是原子事务（见 §3.5）。

代价：慢查询会阻塞事件循环。对家庭单用户规模，无所谓。

## 3.2 连接工厂逐行（src/db/index.ts）

```ts
import Database from 'better-sqlite3';

export function openDb(dbPath: string): Database.Database {
  const abs = resolve(dbPath);                       // 相对路径转绝对
  mkdirSync(dirname(abs), { recursive: true });      // 目录不存在先建
  const db = new Database(abs);                      // 打开/创建库文件
  db.pragma('journal_mode = WAL');                   // ★ WAL 日志模式
  db.pragma('foreign_keys = ON');                    // ★ 开外键（SQLite 默认关）
  db.pragma('busy_timeout = 5000');                  // 锁等待 5 秒
  return db;
}
```

三个 pragma（SQLite 的运行时开关）都要懂：

- **WAL（Write-Ahead Logging，预写日志）**：默认模式（journal）下，写操作要拿到"整库排他锁"，读写互相阻塞；WAL 模式下写操作只追加到独立的 `-wal` 文件，**读者照常读主库**，写者之间也基本不互斥（一个写者）。崩溃时 WAL 也能保证一致性（靠校验和重放）。代价是多两个伴生文件（`-wal`/`-shm`）——**备份时要连它们一起或先 checkpoint**。
- **foreign_keys = ON**：SQLite 出于向后兼容默认**不检查外键**，你必须显式打开，否则 `REFERENCES` 形同虚设（删父表行、插非法子表行都不会报错，数据会烂）。
- **busy_timeout**：遇到锁等待时阻塞多久而不是立刻报 `SQLITE_BUSY`。

## 3.3 Prepared Statement：防注入的根本手段

**SQL 注入**：把用户输入拼进 SQL 字符串，输入里带 `' OR 1=1 --` 之类就会改变语义。防法：**参数化查询**——SQL 模板先编译（prepare），值通过占位符绑定，数据库引擎把值当"数据"而非"代码"处理：

```ts
// ❌ 危险：字符串拼接
db.prepare(`SELECT * FROM accounts WHERE name = '${userInput}'`).get();

// ✅ 安全：占位符绑定（本项目的唯一写法）
db.prepare('SELECT * FROM accounts WHERE name = ?').get(userInput);
```

`prepare` 还会把 SQL **预编译成字节码缓存**，重复执行更快。better-sqlite3 的 API 三元组：

| 方法 | 用途 | 返回 |
|---|---|---|
| `.get(...args)` | 查一行 | 对象 or undefined |
| `.all(...args)` | 查多行 | 对象数组 |
| `.run(...args)` | 增删改 | `{ changes, lastInsertRowid }` |

## 3.4 迁移机制（src/db/migrations.ts）

**问题**：代码和数据库结构要同步进化。直接改表文件？旧库没有新列会崩。**迁移（migration）**= 结构变更的版本管理：

```
src/db/migrations/
  001_init.sql         -- 建核心表
  002_memory_fts_trigram.sql
  003_drop_memory.sql  -- 某轮决定不要 memory 表，用"反向迁移"删掉
  004_drop_profile.sql
  005_work_bills.sql   -- 新增工作记账域（5 张表）
```

runner 逻辑（migrations.ts `applyMigrations`）：

```ts
db.exec(`CREATE TABLE IF NOT EXISTS schema_migrations (version INTEGER PRIMARY KEY, ...)`);
//   ↑ runner 自己的"账本"表：记录哪些版本已执行

const applied = new Set(已执行版本号);            // 从 schema_migrations 读出
const files = readdirSync(dir).filter(文件名匹配 /^\d+_.+\.sql$/)
              .sort(按版本号升序);                 // 严格按版本顺序

const run = db.transaction(() => {               // 整个迁移过程是原子事务
  for (const file of files) {
    const version = Number(file.split('_')[0]);
    if (applied.has(version)) continue;          // 已执行过就跳过（幂等）
    db.exec(readFileSync(...));                   // 执行 SQL
    db.prepare('INSERT INTO schema_migrations ...').run(version, file);  // 记账
  }
});
run();
```

教学点：

- **启动时自动跑**：`index.ts` 里 `applyMigrations(db)` 在服务启动前调用——保证任何环境打开库就是最新结构。
- **幂等**：重复启动不会重复执行（版本号查重）。
- **铁律：永远新增 `00N_xxx.sql`，不要修改已应用的旧文件**——改了旧文件也不会重跑，等于白改，还会造成"不同机器库结构不一致"。
- 迁移文件里可以用"反向操作"（DROP TABLE）来撤销功能——002 建了 FTS 记忆表，003 决定不要了就直接 DROP（这类"推翻重来"在早期迭代很常见）。

## 3.5 事务：`db.transaction()`

多语句要一起成功/一起失败时用事务。better-sqlite3 的事务就是**包一个同步函数**：

```ts
// work_bills.ts：新建账单 + 插入明细，要么都成要么都回滚
const run = db.transaction(() => {
  const billId = insert 主表(...);
  insertItems(db, billId, items);   // 明细
  return billId;
});
const id = run();   // 调用一次，全部提交
```

`db.transaction(fn)` 返回一个"事务化"的新函数：调用它时自动 BEGIN，fn 抛异常自动 ROLLBACK，正常返回自动 COMMIT。**这也是同步 API 的红利**——异步下事务边界要小心处理，同步下闭包一包就是原子操作。

## 3.6 表注册机制（src/db/registry.ts）：给"简单表"开的后门

有些业务（比如未来的"体重记录"）就是一张表 + 增删改查，不值得手写 DAO。项目做了一个**描述符驱动的自举机制**：

```ts
interface TableDescriptor {
  name: string;
  columns: Record<string, ColumnDef>;   // 列定义：类型/默认值/主键/外键
  indexes?: IndexDef[];
  softDelete?: boolean;                 // 声明式软删除（自动加 is_deleted/deleted_at）
}

// 用法（internal/routes.ts 暴露了 HTTP 入口）
registry.register({
  name: 'weight_log',
  columns: { person_id: 'INTEGER', kg: 'REAL', note: 'TEXT' },
  softDelete: true,
});
// 之后自动：建表 + 建索引 + 持久化描述符 + 生成 insert/getById/list/update/delete/count
```

实现要点（registry.ts）：

- `normalizeDescriptor`：校验描述符合法性（表名/列名正则白名单、id 约定 INTEGER PRIMARY KEY AUTOINCREMENT）——**描述符来自外部输入时，必须校验，否则就是 SQL 注入入口**（列名拼进 `CREATE TABLE` 字符串）。
- `buildCreateSql`：把描述符拼成 `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX` SQL。
- `createCrud`：返回一个闭包，内部按描述符动态拼 SQL 实现 7 个通用方法；`softDelete` 时 `list()` 自动加 `is_deleted = 0`、`delete()` 变成 UPDATE 标记。
- 描述符 JSON 存进 `registered_tables` 表（**元数据存进数据库自己**），重启 `loadPersisted()` 读回并幂等重建。

> 设计意图：**核心零改动**地扩展简单域。复杂域（bills 等）因有统计/AA/对账等逻辑仍手写 DAO——两条路按复杂度分流。

# 第 4 章 错误处理与日志

## 4.1 业务错误：AppError

HTTP 错误要"带着业务含义"传给调用方（插件/页面）。项目定义统一错误类：

```ts
// src/lib/errors.ts —— 就这么短
export class AppError extends Error {
  constructor(
    public readonly statusCode: number,   // HTTP 状态码
    public readonly code: string,         // 机器可读错误码，如 'FORBIDDEN'
    message: string,                      // 人类可读信息
  ) {
    super(message);
    this.name = 'AppError';
  }
}
```

用法：业务代码里 `throw new AppError(403, 'FORBIDDEN', '无权访问该账本')`。

## 4.2 全局错误钩子（app.ts `setErrorHandler`）

所有抛出的错误最终汇聚到这里统一格式：

```ts
app.setErrorHandler((err, req, reply) => {
  if (err instanceof AppError) {                          // 我们的业务错误
    void reply.code(err.statusCode).send({ code: err.code, message: err.message });
    return;
  }
  req.log.error(err);                                     // 非业务错误：记日志
  const anyErr = err as { code?: unknown; statusCode?: unknown; message?: string };
  const code = typeof anyErr.code === 'string' ? anyErr.code : 'INTERNAL';
  const status = Number.isInteger(anyErr.statusCode) && anyErr.statusCode >= 400
    ? anyErr.statusCode : 500;                            // 保留 Fastify 自己的 4xx，兜底 500
  void reply.code(status).send({ code, message: anyErr.message ?? 'Internal server error' });
});
```

教学点：

- 所有错误响应统一 `{ code, message }` 结构 → 插件解析逻辑只需写一次。
- **不要把客户端错误误报成 500**：Fastify 自带的 400（如 JSON 解析失败）保留原状态码，只有真正的服务器异常才 500——否则监控/日志会被 4xx 刷爆。

## 4.3 宽容 JSON 解析（app.ts）

```ts
app.addContentTypeParser('application/json', { parseAs: 'string' }, (_req, body, done) => {
  if (body === '' || body === undefined) return done(null, {});  // 空 body → {}
  try { done(null, JSON.parse(body as string)); }
  catch (err) { done(err as Error); }
});
```

很多客户端（尤其 DELETE 无 body）会发 `Content-Type: application/json` 但 body 为空，Fastify 默认报 400 "Body cannot be empty"。这里把空 body 解析成 `{}`，缺字段交给各路由的业务校验兜底——**框架层宽容，业务层严格**。

## 4.4 日志：pino

pino 是高性能 JSON 日志器（Node 生态里最快的之一）。本项目：

```ts
const app = Fastify({
  logger: {
    level: config.logLevel,
    serializers: {
      // 关键：请求日志里把 URL 中的 /w/<64位token> 打码
      req(request) {
        return { method: request.method, url: request.url.replace(/\/w\/[0-9a-f]{64}/gi, '/w/<redacted>') };
      },
    },
    ...(isDev ? { transport: { target: 'pino-pretty', options: {...} } } : {}),
    // 开发时用 pino-pretty 把 JSON 渲染成彩色可读文本；生产保持纯 JSON 便于采集
  },
});
```

教学点：

- **serializers**：pino 的"日志序列化钩子"，在落日志前改写字段——这里把令牌打码，**防止 URL 里的凭证写进日志文件**。
- 开发/生产日志形态不同（pretty vs JSON），通过 `NODE_ENV !== 'production'` 切换。

# 第 5 章 鉴权：三个问题三种答案

这个系统有**三类客户端**，各自需要不同的"你是谁"证明。理解这张表=理解全部鉴权代码：

| 客户端 | 怎么证明身份 | 用的凭证 | 文件 |
|---|---|---|---|
| 插件（服务程序） | 持有共享密钥 | `Authorization: Bearer <X_API_KEY>` | lib/auth.ts |
| 插件代用户操作 | 密钥 + 用户身份头 | `x-platform` + `x-openid` | lib/identity.ts |
| 浏览器开网页 | 能力令牌 | URL 里的 `/w/<token>` | bills_web/tokens.ts |

## 5.1 密钥鉴权（lib/auth.ts）

```ts
function safeEqual(a: string, b: string): boolean {
  const ba = Buffer.from(a), bb = Buffer.from(b);
  if (ba.length !== bb.length) return false;
  return timingSafeEqual(ba, bb);          // ★ 常数时间比较
}
```

- `timingSafeEqual` 防**时序侧信道**：普通 `===` 字符串比较是逐字符的，"前几个字符相同"会提前返回，攻击者可测量响应耗时逐步猜出密钥。`timingSafeEqual` 保证任何输入耗时相同。
- 用法：`preHandler: requireApiKey(apiKey)` 返回一个"鉴权钩子"，不匹配直接 401。

## 5.2 身份注入（lib/identity.ts）

插件在**每个请求**上带 `x-platform`（wechat/qq）+ `x-openid`（平台用户 ID），后端据此查 `person_identities` 解析出 `person_id`：

```ts
async function requireIdentity(req, _reply) {
  const platform = req.headers['x-platform'];
  const openid = req.headers['x-openid'];
  if (typeof platform !== 'string' || typeof openid !== 'string' || openid.length === 0)
    throw new AppError(400, 'IDENTITY_REQUIRED', '缺少 x-platform / x-openid 请求头');
  if (!VALID_PLATFORMS.has(platform)) throw new AppError(400, 'INVALID_PLATFORM', ...);
  const resolved = resolveIdentityByPlatform(db, platform, openid);
  req.identity = { platform, openid, personId: resolved?.person_id ?? null, disabled: resolved?.disabled ?? false };
  //               ↑ 把解析结果挂到请求对象上，后续 handler 直接 req.identity 用
}

async function requireBoundPerson(req, reply) {
  await requireIdentity(req, reply);        // 先解析
  if (!req.identity || req.identity.personId === null)
    throw new AppError(401, 'IDENTITY_UNBOUND', '当前身份尚未绑定 person');
  if (req.identity.disabled) throw new AppError(403, 'PERSON_DISABLED', '该账号已被禁用');
}
```

教学点：

- **身份由基础设施注入，不靠 LLM 猜**（插件注释里强调的设计决策）——防止大模型幻觉出"谁是谁"。
- **装饰器（decorateRequest）**：`app.decorateRequest('identity', null)` 让 TypeScript 知道 `req.identity` 存在；`declare module 'fastify'` 是 TS 的"模块增强"，给第三方类型补字段。
- 两个钩子一宽一严：`requireIdentity`（只要头合法，未绑定也放行，用于引导注册）；`requireBoundPerson`（还要已绑定 + 未禁用，业务接口用这个）。

## 5.3 数据权限核心：resolveAccountId（system/accounts.ts）

鉴权解决了"你是谁"，还要解决"你能动哪个账本"。`resolveAccountId` 是**所有写操作**的公共关卡：

```ts
export function resolveAccountId(db, personId, accountId?): number {
  if (accountId !== undefined) {
    const account = getAccount(db, accountId);
    if (!account) throw new AppError(404, 'ACCOUNT_NOT_FOUND', '找不到该账本');
    const accessible = account.type === 'personal'
      ? account.owner_person_id === personId              // 个人账本：owner 本人
      : isAccountMember(db, accountId, personId);         // 家庭账本：成员表里有
    if (!accessible) throw new AppError(403, 'FORBIDDEN', '无权访问该账本');
    return account.id;
  }
  // 没给 account_id：唯一账本直接用；0 个报错；多个报"请指定"（让 LLM 反问）
  const accounts = listAccountsForPerson(db, personId);
  if (accounts.length === 0) throw new AppError(400, 'NO_ACCOUNT', '还没有任何账本');
  if (accounts.length > 1) throw new AppError(409, 'ACCOUNT_AMBIGUOUS', '有多个可用账本，请指定 account_id');
  return accounts[0]!.id;
}
```

**权限模型**：personal 账户 owner 隐含（无成员表）；family 账户靠 `account_members` 显式授权（`listAccountsForPerson` 的 SQL：`personal 走 owner_person_id UNION family 走成员表`）。所有业务路由先调它，**跨账户越权在架构上不可能**。

# 第 6 章 第一个业务模块：日常记账（bills）

这一章我们把一个业务域从表到 HTTP 完整走一遍。**读懂这一章 = 读懂所有业务域**，因为 tasks / work_bills / news 都是同一套模式：`表 → DAO → 路由 → 被调用`。

## 6.1 表设计（001_init.sql §4.5）

```sql
CREATE TABLE bills (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id    INTEGER NOT NULL REFERENCES accounts(id),
  person_id     INTEGER NOT NULL REFERENCES persons(id),   -- 记录人（=垫付者）
  type          TEXT NOT NULL DEFAULT 'expense',         -- 'income'|'expense'
  amount        INTEGER NOT NULL,                        -- 单位：分
  category      TEXT NOT NULL DEFAULT '其他',
  note          TEXT NOT NULL DEFAULT '',
  occurred_at   TEXT NOT NULL,                           -- 发生时间
  status        TEXT NOT NULL DEFAULT 'settled',         -- 'settled'|'pending'（AA）
  participants  TEXT NOT NULL DEFAULT '[]',              -- JSON：[{name,status,paid_at}]
  is_deleted    INTEGER NOT NULL DEFAULT 0,              -- 软删除标记
  deleted_at    TEXT,
  created_at    TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at    TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
```

**每个设计决定都值得展开**：

1. **`amount` 用分（INTEGER）而不是元（REAL）**：浮点数 `0.1 + 0.2 !== 0.3`，金额用浮点会累积误差。整数分是"精确金额"的标准做法。全项目统一此约定。
2. **`occurred_at` 用 TEXT 存 `YYYY-MM-DD HH:MM:SS`**：SQLite 没有真正的日期类型，用 ISO 格式文本 + 字典序比较 = 时间比较。`datetime('now','localtime')` 是本地时间的 SQLite 写法。
3. **`participants` 是 JSON 文本**：SQLite 没有数组列。AA 分摊的参与人数组序列化成 JSON 存 TEXT。项目提供 `parseParticipants`/`normalizeParticipants` 封装（后面看 settleBill 怎么用它）。
4. **软删除**：`is_deleted + deleted_at`。删除 = UPDATE 置 1（可恢复，进回收站）；**物理删除**（purge）才是 DELETE。两级语义：用户删除进回收站，调度器定时硬删超期记录（§11）。
5. **`created_at/updated_at` 用 SQLite 默认值**（`datetime('now','localtime')`），应用层不用管插入时间。

## 6.2 DAO：bills.ts 教学

DAO（Data Access Object）= 把"对 bills 表的所有操作"封装成纯函数。业务代码（路由/调度器/Web）永远不写裸 SQL，只调这些函数——**换数据库、改表结构时，改动面收敛在一个文件**。

### 6.2.1 金额与 CSV 工具（先讲两个小函数）

```ts
export function yuan(fen: number): string {
  const sign = fen < 0 ? '-' : '';
  const abs = Math.abs(fen);
  const int = Math.floor(abs / 100);
  const frac = abs % 100;
  return frac === 0 ? `${sign}${int}` : `${sign}${int}.${String(frac).padStart(2, '0')}`;
  // 1200 分 → "12"；120050 分 → "1200.50"（非整才保留两位）
}

export function csvCell(v: string): string {
  return /^[=+\-@]/.test(v) ? `'${v}` : v;   // CSV 公式注入防护
}
```

- `yuan`：分→元字符串，整数不带小数、非整保留两位——显示层统一用它，别处不再做金额格式。
- `csvCell`：**CSV 注入**——如果单元格内容以 `=` 开头（如 `=HYPERLINK(...)`），Excel 打开时会把它当公式执行。导出前给这类单元格加 `'` 前缀变成纯文本。这是"用户输入进 Excel"场景的必防攻击面。

### 6.2.2 筛选构建器：`buildBillFilter`（"筛选=导出"同源的秘密）

```ts
export function buildBillFilter(q: BillListQuery): { conds: string[]; args: unknown[] } {
  const conds: string[] = ['is_deleted = 0'];        // 打底：过滤软删
  const args: unknown[] = [];
  if (q.month) { conds.push("substr(occurred_at,1,7) = ?"); args.push(q.month); }
  if (q.category) { conds.push('category = ?'); args.push(q.category); }
  if (q.type) { conds.push('type = ?'); args.push(q.type); }
  // ...金额区间、状态、参与人（JSON 里 LIKE）等
  return { conds, args };      // 返回「条件数组 + 参数数组」，二者按下标配对
}
```

它不直接执行 SQL，而是**返回可拼接的 WHERE 片段**。这样 `listBills`（分页列表）和 `exportBills`（全量导出）共用同一套条件：

```ts
export function listBills(db, accountId, q) {
  const { conds, args } = buildBillFilter(q);
  // ... WHERE account_id=? AND <conds> ORDER BY ... LIMIT ? OFFSET ?
}

export function exportBills(db, accountId, q = {}) {
  const { conds, args } = buildBillFilter(q);
  // ...同样的条件，只是没有 LIMIT/OFFSET，且按日期升序
}
```

**这就是 Web 面"页面筛选所见即所导"的实现基础**（§12 会用到）：页面把筛选参数传给列表，导出按钮把同样的参数传给导出接口，两个函数底层是同一份过滤逻辑，不可能"页面筛的和导出导的不一致"。

### 6.2.3 AA 结算：`settleBill`（状态是派生的）

AA（平摊）账单的参与人状态存在 JSON 里，结算逻辑：

```ts
export function settleBill(db, billId, input) {
  const before = getActiveBill(db, billId);
  const participants = parseParticipants(before.participants);   // JSON → 对象数组
  if (participants.length === 0) throw new AppError(400, 'NOT_AA_BILL', '该账单没有待结算参与人');

  if (input.all === true) {
    for (const p of participants) { p.status = 'paid'; p.paid_at = p.paid_at ?? now(); }
  } else if (typeof input.participantName === 'string' && input.participantName.trim()) {
    const target = participants.find((p) => p.name === input.participantName.trim());
    if (!target) throw new AppError(404, 'PARTICIPANT_NOT_FOUND', `参与人不存在: ${input.participantName}`);
    if (target.status !== 'paid') { target.status = 'paid'; target.paid_at = now(); }
  } else {
    throw new AppError(400, 'INVALID_BODY', '需提供 participant_name 或 all:true');
  }

  const after = { ...before,
    participants: JSON.stringify(participants),
    status: participants.every((p) => p.status === 'paid') ? 'settled' : 'pending',  // ★ 派生
    updated_at: now(),
  };
  db.prepare('UPDATE bills SET status = ?, participants = ?, updated_at = ? WHERE id = ?')
    .run(after.status, after.participants, after.updated_at, billId);
  return { before, after };
}
```

教学点：

- **状态不靠用户手填**：`status` 由"是否全部参与人已付"派生。这避免了"状态与明细不一致"的状态一致性问题。
- `parseParticipants` 内部 `JSON.parse` 带 try/catch 兜底（脏数据不崩）。
- 返回 `{ before, after }` 供路由写审计日志（operation_logs 的 before_data/after_data）。

### 6.2.4 统计：`billStats`

```ts
export function billStats(db, accountId, q) {
  // 一条 SQL 同时拿：收入合计 / 支出合计 / 按分类聚合 / 按月趋势
  const income = SUM(amount WHERE type='income' AND 筛选) ...
```

## 6.3 路由层：一个完整 API 的解剖

看 `POST /api/v1/bills`（bills/routes.ts:71）：

```ts

  logOperation(db, { personId, accountId, action: 'bill.create',   // ⑤ 审计
    entity: 'bills', entityId: billId, after: getActiveBill(db, billId) });
  return reply.code(201).send({ bill: toOut(getActiveBill(db, billId)!) });  // ⑥ 响应
});
```

一个路由的固定六步（**本项目所有写路由都是这个模式**）：

1. **取身份**：`req.identity` 是 preHandler 注入的（§5.2）。
2. **过权限**：`resolveAccountId` 决定 account_id（没有就按"唯一/多账本"策略处理）。
3. **调 DAO**：业务逻辑全在 DAO，路由不写 SQL。
4. **输入归一**：把外部输入转成 DAO 要的形状（元→分、枚举白名单、缺省值）。**宽容解析**：非法值取默认而不是报错——这是"面向 LLM 调用"的设计（插件传参不可靠，能救就救）。
5. **审计**：`logOperation` 写 before/after 快照（日报的数据源，§11）。
6. **响应**：返回前端友好的形状（`toOut` 把"分"转回"元"、格式化时间）。

**完整调用示例**（插件实际就是这么调的，见第 9 章）：

## 7.2 remind_at 的严格校验（一个真实踩坑案例）

```ts
export function normalizeRemindAt(input?: unknown): string | null {
  if (input === undefined || input === null || input === '') return null;
  const s = String(input).trim();
  if (!/^\d{4}-\d{2}-\d{2}( \d{2}:\d{2}(:\d{2})?)?$/.test(s)) {
    throw new AppError(400, 'INVALID_REMIND_AT', 'remind_at 需为 YYYY-MM-DD 或 YYYY-MM-DD HH:MM');
  }
  const base = s.slice(0, 10);
  const time = s.length > 10 ? s.slice(11).padEnd(8, ':00') : '00:00:00';
  return `${base} ${time}`;    // 归一成完整 "YYYY-MM-DD HH:MM:SS"
}
```

- 正则严格限定格式：`YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM[:SS]`，**不接受 `T` 分隔符**。
- **真实事故**：Web 表单曾用 `<input type="datetime-local">`，它提交 `2026-08-20T09:00`（带 T），后端正则拒绝 → 用户添加/编辑待办必报错。修法：表单改 `text` + placeholder 提示格式（§12）。
- 教训：**前端控件格式 ≠ 后端校验格式**，这类边界在项目里是高频坑。

## 7.3 幂等提醒的配合

`reminded` 字段 + 调度器 `runReminderDue`（§11.3）组成"到点提醒一次"的闭环：调度器扫描 `remind_at <= now AND reminded = 0 AND is_done = 0 AND is_deleted = 0`，写入 outbox 后立刻置 `reminded = 1`。**"有状态标记"让定时任务天然幂等**——即使调度器被反复触发，每任务也只提醒一次。

装修安装场景的专门记账域：**委托方 → 单价表 → 账单 → 明细 → 结算** 五张表（005_work_bills.sql）。

## 8.1 数据模型：快照与派生的设计


**对账公式**（work_bills.ts `calcLedger`，全项目唯一计算点）：

```ts
function calcLedger(finalAmount, computedTotal, paid): WorkBillLedger {
  const receivable = finalAmount ?? computedTotal;      // 应收：显式 final_amount 优先，否则 Σ明细
  const owed = receivable - paid;                        // 欠款
  const status = paid <= 0 ? 'unsettled' : paid >= receivable ? 'settled' : 'partial';
  return { computed_total, receivable, paid, owed, status };
}
```

列表页、统计页、导出 CSV、recalc 全部复用这一个函数 → **任何页面看到的应收/已收/欠款数字必然一致**。这是"单一事实来源（single source of truth）"的实践。

## 8.2 单价表联动：快照 vs 引用

新建账单明细时：

```ts
if (it.unit_price === undefined || it.unit_price === null) {
  // 没填单价 → 查单价表带出
  const price = lookupUnitPrice(db, accountId, clientId, name);

```

**设计权衡（重要）**：

- 明细存的是**单价快照**（unit_price 直接落库），不是"每次显示都去查单价表"——历史账单不受单价表后续修改影响（账要稳定）。
- 同时存 `price_ref_id` 引用——需要时（`POST /api/v1/work-bills/recalc`）可以按单价表**重算**全账户账单，实现"批量调价"。
- 这就是经典的 **快照 + 引用 双轨**：显示用快照（稳定），重算用引用（可控）。

# 第 9 章 出站消息与插件闭环

## 9.1 为什么需要 outbox（出站队列）

后端跑在 Docker 容器里，**无法直连 IM 平台**（QQ/微信的机器人协议在插件进程里）。如果后端要"主动"发消息（提醒、日报），必须有个中间地带：后端写"待发消息"进表，插件定时来取、投递、回执。这就是 **outbox（发件箱）模式**，本质是**生产-消费（producer-consumer）**：

```
后端（生产者）                   插件（消费者）
 任务到期 → enqueue(outbox表)  →  轮询 /api/v1/outbox/pending
                                    取走 → 调 IM 平台 API 发消息
                                    回执 POST /delivery（sent/failed）
```

好处：解耦（后端不认识 IM）、可重试（attempts 计数）、可审计（状态流转全程留痕）。

## 9.2 outbox 生产侧（src/modules/outbox/index.ts）

# 第 10 章 新闻订阅与适配器模式

## 10.1 问题

系统要抓多个数据源（通用 RSS、Steam 新闻、预设站点…），每个源的协议/解析完全不同。如果写死在业务代码里，加一个源就要改核心代码。

**策略模式（Strategy）**解法：定义一个统一接口，每种源是一个实现，注册表按 key 取用。

## 10.2 契约（news/adapters/types.ts）

```ts
export interface FetchedItem {
  title: string;                    // 必填
  url: string;                      // 必填：去重键（上层 sha256(url)）
  summary?: string;                 // 可选摘要（纯文本，不带 HTML）
  published_at?: string | null;
}

export interface FetchAdapter {
  key: string;                      // 唯一键，订阅的 preset_key 指向它
  label: string;                    // 展示名
  fetch(params?: Record<string, unknown>): Promise<FetchedItem[]>;
  // 失败一律 throw（中文可读 message），上层捕获记日志
}
```

**"面向接口编程"**：业务代码只依赖 `FetchAdapter` 接口，不关心具体实现。新增数据源 = 新建文件实现接口 + 注册表登记，**核心代码零改动**。

## 10.3 一个完整实现：rss.ts 教学

`rss` 适配器负责把 RSS/Atom/XML 解析成 `FetchedItem[]`：

```ts
import { XMLParser } from 'fast-xml-parser';   // XML → JS 对象

const parser = new XMLParser({
  removeNSPrefix: true,        // 去掉命名空间前缀（dc:date → date）
  isArray: (name) => name === 'item' || name === 'entry',  // 单条也恒为数组
  // ...
});

export function parseFeed(xml: string): FetchedItem[] {
  const root = parser.parse(xml);
  // 三种格式自动识别（根元素名不同）：
  if (root.rss)    → RSS 2.0：rss.channel.item[]      → rss2Item 映射
  if (root.feed)   → Atom：feed.entry[]               → atomEntry 映射
  if (root.RDF)    → RSS 1.0：RDF.item[]              → rss2Item 映射
  throw new Error('RSS 解析失败: 无法识别的 feed 格式');
}

function rss2Item(item): FetchedItem | null {
  const title = cleanHtml(asText(item.title));        // 剥 HTML 标签
  const link = asText(item.link) || asText(item.guid);
  if (!title && !link) return null;                    // 标题和链接都没有 → 丢弃
  const summary = truncate(cleanHtml(asText(item.description)));
  return { title: title || '(无标题)', url: link, summary, published_at: ... };
}

export const rss: FetchAdapter = {
  key: 'rss', label: '通用 RSS/Atom',
  async fetch(params) {
    const sourceUrl = params?.source_url;
    if (typeof sourceUrl !== 'string' || !sourceUrl.trim())
      throw new Error('rss 适配器: 缺少参数 source_url');
    if (!/^https?:\/\//i.test(sourceUrl))
      throw new Error(`rss 适配器: source_url 需为 http(s) 地址`);
    const xml = await fetchText(sourceUrl);            // 带 UA 抓取（防 Cloudflare 403）
    return parseFeed(xml);
  },
};
```

教学点：

- **格式识别靠根元素名**：RSS 2.0 根是 `<rss>`，Atom 是 `<feed>`，RSS 1.0 是 `<RDF>`——一次解析兼容三种格式。
- **容错**：标题/链接全缺的条目丢弃（`return null` + 上层 filter）；HTML 摘要剥标签截断，**不把 HTML 传给下游**（防注入 + 消息格式干净）。
- **`isArray` 配置**：XML 里只有一个 `<item>` 时 fast-xml-parser 默认给对象而非数组，强制恒为数组避免 `items.map` 崩。

# 第 11 章 调度器：让系统自己动起来

## 11.1 node-cron：cron 表达式

`node-cron` 是 Node 的 cron 库。**cron 表达式**（5 个字段：分 时 日 月 周）：

```
* * * * *     每分钟
*/5 * * * *   每 5 分钟
0 4 * * *     每天凌晨 4 点
0 */6 * * *   每 6 小时
```

`cron.schedule(表达式, fn, { timezone })` 注册任务，返回的 job 可 `stop()`。

## 11.2 调度器骨架（src/scheduler/index.ts）

```ts
class Scheduler {
  private jobs: cron.ScheduledTask[] = [];

  start(): void {
    const opts = { timezone: this.timezone };          // 统一时区（Asia/Shanghai）
    this.jobs.push(cron.schedule('* * * * *',
      () => safeRun('reminder_due', () => runReminderDue(this.db), this.log), opts));
    // ... 其他任务
  }

  stop(): void { for (const job of this.jobs) job.stop(); this.jobs = []; }
}

// ★ 关键兜底：单个任务失败只记日志，绝不让 cron 循环崩掉
async function safeRun(name, fn, log) {
  try { const n = await fn(); if (n > 0) log(`[scheduler:${name}] 完成 ${n} 条`); }
  catch (err) { log(`[scheduler:${name}] 失败: ${(err as Error).message}`); }
}
```

**为什么 safeRun 是底线**：node-cron 的回调如果抛异常（未捕获），可能让整个调度循环异常退出——一个任务炸了，所有定时功能全停。每个任务包 try/catch 是必须的。

## 11.3 任务实现教学：runReminderDue（提醒）

```ts
export function runReminderDue(db): number {
  // ① 扫出"到点、未提醒、未完成、未删除"的任务
  const due = db.prepare(
    `SELECT * FROM tasks
     WHERE remind_at IS NOT NULL AND remind_at <= ? AND reminded = 0
       AND is_done = 0 AND is_deleted = 0`
  ).all(now());

  let count = 0;
  for (const task of due) {
    // ② 定位推送目标：任务创建平台 → 该平台 openid；找不到回落主平台；再找不到跳过
    let identity = task.platform ? identityOn(db, task.creator_id, task.platform) : undefined;
    if (!identity) identity = primaryIdentity(db, task.creator_id);
    if (!identity) continue;

    enqueue(db, {                              // ③ 写 outbox（生产侧，§9）
      personId: task.creator_id, channel: identity.platform,
      targetId: identity.openid, kind: 'reminder',
      content: `【提醒】${task.category ? `[${task.category}] ` : ''}${task.content}`,
    });
    db.prepare('UPDATE tasks SET reminded = 1 WHERE id = ?').run(task.id);  // ④ 防重复
    count++;
  }
  return count;
}
```

四步模式（**所有调度任务通用**）：扫条件 → 找目标 → 产生动作（写 outbox / 清理）→ 打状态标记（幂等）。

## 11.4 任务实现教学：runBillDigest（日报，读审计表）

```ts
  // ③ 从审计表找出"当日有 bills 变动"的账户（这就是为什么要 logOperation！）
  const changedAccounts = SELECT DISTINCT account_id FROM operation_logs
    WHERE entity='bills' AND account_id IS NOT NULL AND substr(created_at,1,10) = ?;

  // ④ 汇总接收人：家庭账本=全部成员，个人账本=本人
  const recipients = new Set<number>();
  for (const { account_id } of changedAccounts) {
    const account = ...;
    if (account.type === 'family') { 成员表 → 全部加入 }
    else { recipients.add(account.owner_person_id); }
  }

  // ⑤ 每个接收人：当日已发过？→ 跳过（幂等）；组装日报文本 → enqueue
  for (const personId of recipients) {
    if (alreadySentToday(db, personId, 'bill_digest')) continue;
    const { changes } = billChanges(db, personId, date);   // §6 的 billChanges
    const text = formatBillDigest(date, changes);
    if (!text) continue;
    enqueue(db, { ..., kind: 'bill_digest', content: text });
    sent++;
  }
  return sent;
}
```

教学点：

- **日报数据来自审计表**：`billChanges` 读 `operation_logs` 生成"新增 X 笔/修改 Y 笔/AA 结算 Z 笔"——所以 §6.3 的"写操作记日志"不是摆设，它是日报/简报的数据基础。

- **settings 动态配置**：推送时刻存 settings 表，运行时改立即生效（不用重启）。

# 第 12 章 记账 Web 面

## 12.1 为什么有 Web 面，为什么它"零 JS"

IM 对话界面不适合表格/筛选/统计/导出。Web 面给浏览器一个可视化界面。模块在 `src/modules/bills_web/`。

**最关键的约束**：响应头带 `Content-Security-Policy: script-src 'none'`——页面**禁止执行任何 JavaScript**。为什么？

- Web 面的凭证是 URL 里的能力令牌（`/w/<token>`）。如果页面允许脚本，一旦某个字段渲染漏转义被 XSS 注入 `<script>`，恶意脚本就能读 URL 偷令牌、伪造请求。
- 禁掉 JS 后，即使出现 XSS，攻击面也只剩"改页面显示"，拿不到凭证。
- 交互全部用原生 HTML 完成：`<form>` 提交、`<a>` 跳转、`<datalist>` 联想、`required` 校验。

**给不熟悉的人**：CSP（Content-Security-Policy）是浏览器安全机制，通过响应头告诉浏览器"这个页面允许加载/执行什么"；`script-src 'none'` = 禁止一切脚本。这是"不用 JS 也能做完整交互"的现代 HTML 能力 + 安全取舍。

## 12.2 能力令牌（tokens.ts）：Web 面安全的基石

Web 面没有用户名密码，用**能力令牌**——"持 URL 即有权"：

```ts
export function mintToken(db, personId, mode, expiresInMinutes): MintResult {
  const token = randomBytes(32).toString('hex');   // 256 位随机数
  const hash = sha256(token);                       // ★ 只存哈希
  db.prepare('INSERT INTO web_tokens (person_id, token_hash, mode, expires_at) VALUES (?,?,?,?)')
    .run(personId, hash, mode, expiresAtStr);
  return { id, token, expires_at };                 // 明文仅本次返回（回显一次）
}

export function verifyToken(db, rawToken) {
  const t = String(rawToken ?? '').trim();
  if (!TOKEN_RE.test(t)) return null;               // 格式校验（64 hex），拒绝非法输入
  const row = db.prepare('SELECT * FROM web_tokens WHERE token_hash = ?').get(sha256(t));
  if (!row) return null;
  if (row.expires_at <= now()) return null;          // 过期失效
  db.prepare('UPDATE web_tokens SET last_used_at = ? WHERE id = ?').run(now(), row.id);
  return { personId: row.person_id, mode: row.mode };
}
```

教学点：

- **为什么只存哈希**：数据库泄露时攻击者拿到的是不可逆哈希，无法反推明文 → 无法伪造 URL。这是"能力凭证"的标准实践（同密码只存哈希）。
- **校验路径**：格式正则（拒绝超大输入，防 DoS）→ sha256 → 查库 → 过期判断。全程没有"字符串比较"环节，无时序泄露。
- **mode**：`read|write`，只读令牌不能执行写路由（`requireWrite` 钩子 403）。
- 铸造入口：`POST /api/v1/web/tokens`（需 X-API-Key + 身份头，内部面）；开发时用 `scripts/_mint.cjs` 或 `seed-dev.mjs`。

## 12.3 页面鉴权钩子（routes.ts `webAuth`）

```ts
async function webAuth(req, reply) {
  const token = req.params.token;
  if (!checkRateLimit(req.ip))                       // ① 按 IP 限流（§12.4）
    return reply.code(429).type('text/html').send(errorPage('尝试次数过多，请稍后再试'));
  const session = verifyToken(db, token);
  if (!session) {
    recordFailure(req.ip);                           // ② 失败计数（防爆破）
    return reply.code(401).type('text/html').send(errorPage('链接无效或已过期'));
  }
  clearFailures(req.ip);
  req.web = session;                                 // ③ 挂会话 { personId, mode }
  reply.header('Content-Security-Policy', CSP);      // ④ 安全头
  reply.header('X-Content-Type-Options', 'nosniff');
}
```

写路由再挂 `requireWrite`（mode 校验）。**每个页面路由都过它**。

## 12.4 限流（ratelimit.ts）：纯内存滑动窗口

```ts
const failures = new Map<string, number[]>();        // IP → 失败时间戳数组

export function checkRateLimit(key: string, max = 10, windowMs = 300_000): boolean {
  const cutoff = Date.now() - windowMs;
  const arr = (failures.get(key) ?? []).filter((t) => t > cutoff);  // 只留窗口内的
  failures.set(key, arr);
  return arr.length < max;                            // 窗口内失败 < max 才放行
}
```

**滑动窗口限流**：记每个来源的失败时刻，5 分钟内超过 10 次就 429。纯内存实现（重启清零），对家庭规模足够。`Map` 是 JS 的哈希表容器。

## 12.5 EJS 模板：语法与"怎么返回不同页面"

EJS = "HTML 里嵌 JS"。三种标签（**必须分清**）：

| 标签 | 含义 | 是否转义 |
|---|---|---|
| `<% 代码 %>` | 执行 JS 逻辑（循环/条件），不输出 | — |
| `<%= 表达式 %>` | 输出表达式结果 | ✅ HTML 转义（防 XSS） |
| `<%- 表达式 %>` | 原样输出（**只用于受信任内容**） | ❌ 不转义 |

**"怎么用同一个外壳渲染不同页面"**（这是理解 Web 面的钥匙）——`templates.ts`：

```ts
// 启动时把每个 .ejs 编译成 JS 函数，缓存
export const tpl = {
  layout: load('layout.ejs'),
  bills: load('bills.ejs'),
  overview: load('overview.ejs'),
  tasks: load('tasks.ejs'),
  // ... 18 个模板
};

// 渲染管线：子模板 → body 片段 → 注入 layout 外壳
export function renderPage(title, token, mode, bodyTemplate, data): string {
  const body = bodyTemplate({ token, mode, opt, comma, switcher, active, ...data });
  //            ↑ 子模板就是"一个函数"，喂数据返回 HTML 片段
  return tpl.layout({ title, token, mode, accountId, active, body });
  //            ↑ 外壳模板拿到 body 片段，嵌进 <main><%- body %></main>
}
```

**layout.ejs 就是"同一套页面框架"**：`<head>`（设计系统 CSS 变量）、`<nav>`（顶栏导航）、`<main><%- body %></main>`。不同页面 = 不同的子模板函数 + 不同的数据，但都套同一外壳 → **全站风格统一，导航一致**。

举个例子，bills.ejs 里的一段：

```html
<% items.forEach(function(b){ %>                    <!-- 循环 -->
  <tr>
    <td><%= b.occurred_at %></td>                    <!-- 输出（转义） -->
    <td class="num <%= b.type === 'income' ? 'income' : 'expense' %>">
      <%= b.type === 'income' ? '+' : '-' %><%= comma(b.amountYuan) %>
    </td>
  </tr>
<% }) %>
```

`comma` 是注入的视图助手（§12.7），`b.amountYuan` 是路由准备好的"元"字符串——**模板只做展示，不做业务计算**。

## 12.6 视图助手与 DRY（templates.ts）

`renderPage` 把几个纯函数注入模板作用域，18 个模板共用：

| 助手 | 作用 | 关键实现 |
|---|---|---|
| `opt(accounts, accountId, series?)` | 生成账本 `<option>` 列表；series 传 `'daily'\|'work'\|'task'` 时每账本三行复合选项（"XX · 日常账单 / XX · 工作账单 / XX · 待办"） | 循环拼字符串，值 `daily-N`/`work-N`/`task-N` |
| `comma(v)` | 金额千分位 | `String(v).replace(/\B(?=(\d{3})+(?!\d))/g, ',')`——"非单词边界 + 后跟 3 的倍数位数字"处插逗号 |
| `switcher({...})` | 统一账本切换工具条（form + select + 切换按钮 + 操作链接） | 链接直接渲染 `<a class="btn">`，见反模式 |
| `active` | 当前页在顶栏的高亮键 | layout 用它加 `class="active"` |

**复合账本选择器（(account_id, series) 复合键）**：路由端 `parseAccountSel` 解析 `daily-N/work-N/task-N`：

```ts
function parseAccountSel(raw, pageSeries) {
  if (raw === undefined || raw === '') return { series: pageSeries, id: undefined };
  const m = /^(daily|work|task)-(\d+)$/.exec(raw);
  if (m) return { series: m[1], id: Number(m[2]) };
  return { series: pageSeries, id: Number(raw) };   // 裸数字按页面自身系列（兼容旧链接）
}
```

在账单页选"XX · 工作账单"→ 303 重定向到 `/work?account_id=XX`；三个统计页（日常/工作/待办）互相可跳。**一个下拉切换"账本 × 系列"两个维度**。

## 12.7 反模式教训：`<a><button>` 嵌套（真实 bug）

曾经 work/tasks 页的操作按钮写成：

```html
<a href="/work/stats"><button class="ghost">统计</button></a>   <!-- ❌ -->
```

结果**点击无反应**：`<button>` 默认 `type="submit"`，在表单内会**提交外层表单**（GET 回当前页）而不是跟随 `<a>` 跳转；HTML 规范里 `<a>` 也不能包裹交互元素。

修法（铁律）：**链接用 `<a class="btn">`（样式直接给 a），提交用 `<form><button>`**：

```html
<a class="btn" href="/work/stats">📊 统计</a>                   <!-- ✅ 链接 -->
<form class="inline" method="post" action="/work/42/delete">     <!-- ✅ 提交 -->
  <button class="danger">🗑️</button>
</form>
```

# 第 13 章 构建与部署

## 13.1 `npm run build` 到底发生了什么（逐环节）

```bash
npm run build   # = tsc && node scripts/copy-assets.mjs
```

**环节一：`tsc`（TypeScript 编译器）**

1. 读 `tsconfig.json`（§1.4）。
2. **类型检查**：全项目过一遍类型（strict 模式），有类型错误**直接失败退出**（构建即拦截 bug）。
3. **编译**：把每个 `src/**/*.ts` 转成 `dist/**/*.js`（擦除类型、ESM 转换）。
4. 产出：`.js` + `.map`（sourcemap，调试时浏览器/Node 能映射回 TS 源码）。

**环节二：`copy-assets.mjs`（拷贝非 TS 资产）**

```js
const ASSETS = [
  ['src/db/migrations', 'dist/db/migrations'],                        // 迁移 SQL
  ['src/modules/bills_web/templates', 'dist/modules/bills_web/templates'], // EJS 模板
];
for (const [src, dest] of ASSETS) {
  mkdirSync(dest, { recursive: true });
  cpSync(src, dest, { recursive: true });
}
```

**为什么需要它**：`tsc` 只编译 `.ts`，`.sql` 和 `.ejs` 是**运行时读盘**的资产（migrations.ts 读 SQL、templates.ts 读 EJS），必须原样拷进 dist。**新增这类资产时要在 ASSETS 里登记**。

**产物结构**（dist/ 与 src/ 同构）：

```
dist/
├─ index.js            # 入口（tsc 产物）
├─ app.js
├─ db/migrations/      # 拷来的 .sql
├─ modules/bills_web/
│  ├─ routes.js
│  └─ templates/       # 拷来的 .ejs
└─ ...                 # 其余模块的 .js + .map
```

**启动时序**（index.ts `main()`，为什么这个顺序）：

```
1 loadConfig()          配置（缺密钥抛错=拒绝启动）
2 openDb()              打开 SQLite（WAL/外键）
3 applyMigrations()     迁移（保证库结构最新）
4 registry.loadPersisted()  恢复注册表（幂等建表）
5 buildApp()            Fastify 装配（注册全部路由）
6 new Scheduler().start()  启动定时任务（SCHEDULER_ENABLED 可关）
7 app.listen()          监听端口
8 注册 SIGINT/SIGTERM → 优雅关停（先停调度器，再关 HTTP，再关库）
```

## 13.2 Docker 部署（Dockerfile 逐行）

```dockerfile
FROM node:22-alpine              # 基础镜像（Node 22 + Alpine Linux）
WORKDIR /app
COPY package.json package-lock.json ./   # 先拷清单
RUN npm ci                        # 按 lock 文件精确安装（可复现；ci 比 install 严格）
COPY tsconfig.json ./             # 拷源码 + 构建
COPY scripts ./scripts
COPY src ./src
RUN npm run build                 # 容器内构建（tsc + copy-assets）
RUN rm -rf src scripts tsconfig.json   # 构建完删源码，镜像只留可执行产物（体积小）

CMD ["sh", "-c", "npm run migrate && npm start"]   # 启动前先迁移（幂等），再起服务
```

**教学点**：

- **层缓存**：先拷 `package.json/lock` 再 `npm ci`，之后才拷源码——源码改动不触发依赖重装（Docker 每层缓存）。
- **单阶段构建且保留 devDependencies**：注释里说明故意保留 tsx，使容器内 `npm run migrate/backup` 能跑（操作手册要求 `docker compose exec api npm run migrate`）。
- **启动前跑迁移**：`migrate && start` 保证任何新镜像在旧数据上也能平滑升级。

# 第 14 章 总串联与动手练习

## 14.1 一条完整链路的"全景视角"

**场景：用户中午跟 QQ 机器人说"记一笔：午饭 30，AA 跟小李"，晚上收到日报。**

```
白天 12:30
 QQ 消息 → AstrBot 插件 → LLM 选 add_bill 工具（参数来自 docstring）
 → POST /api/v1/bills { Bearer key, x-platform/x-openid, amount:3000, participants:[小李] }
 → lib/identity 解析 person → resolveAccountId 校验账户
 → bills.ts createBill（分/JSON 落库，status=pending）→ logOperation 审计
 → 插件回复"已记录#42：支出 30（餐饮）AA待结算…"

白天 12:35
 用户："小李给了" → LLM 选 settle_bill → settleBill 标记 paid → 全员付清 → status=settled

晚上 21:00（调度器每 5 分钟检查一次时刻）
 scheduler runBillDigest → 读到 settings 到点 → 查 operation_logs 找当日变动账户
 → 家庭账本→全体成员 → billChanges 汇总文本 → enqueue(outbox)

晚上 21:00:15（插件每 15 秒轮询）
 插件 GET /outbox/pending?channel=qq → 取到日报 → send_message 发 QQ
 → 回执 POST /outbox/:id/delivery { status: sent }

网页侧（家人用浏览器）
 家人打开 /w/<token> → webAuth 验令牌 → overview 每账本三段统计
 → 点"账单"→ bills?account_id=3 → listBills 筛选 → EJS 渲染表格
 → 点"导出当前筛选 CSV" → exportBills → 附件下载
```

**每一环都有明确文件**：插件 main.py → bills/routes.ts → bills/bills.ts → scheduler/tasks.ts → outbox → 插件轮询；Web 面走另一条渲染链但共享 DAO。**这就是"知道改哪个文件"的本质**。

## 14.2 如果你要写一个类似项目（最小骨架）

1. **起服务**：`npm init` + `fastify`，写一个路由（§1.3）。
2. **加类型**：`typescript` + tsconfig（§1.4），`tsx` 开发。
3. **接库**：`better-sqlite3` + openDb（§3.2），迁移 runner（§3.4）。
4. **统一错误**：AppError + setErrorHandler（§4）。
5. **鉴权**：一个密钥钩子 + 一个身份中间件（§5）。
6. **业务域**：表 → DAO（筛选构建器）→ 路由六步（§6.3）。
7. **主动推送**：outbox 表 + enqueue + 消费路由（§9）；调度器 node-cron + safeRun + 幂等标记（§11）。
8. **网页**：EJS + 能力令牌 + CSP 零 JS（§12）。
9. **构建**：tsc + copy-assets + Dockerfile（§13）。

顺序即依赖顺序——每一步都在本教程对应章节有完整代码和讲解。

## B. 数据模型速记

- 金额一律**分（INTEGER）**；时间一律**本地时间 TEXT**；软删除一律 `is_deleted + deleted_at`。
- 家庭账户授权走 `account_members`；personal 账户 owner 隐含。
- AA 参与人 = bills.participants JSON；工作账单对账 = 派生值（calcLedger）。
- outbox = 后端→插件的唯一推送通道（生产-消费）。
- operation_logs = 审计 + 日报数据源（写操作必记）。

## C. 术语表

| 术语 | 含义 |
|---|---|
| 事件循环 | Node 单线程的异步调度机制（§0.1） |
| ESM / CommonJS | 两种 JS 模块系统；本项目用 ESM |
| transpile | 转译：TS→JS（本项目 tsx/tsc 都做） |
| 装饰器 decorateRequest | Fastify 扩展请求对象 |
| preHandler | Fastify 路由前置钩子（鉴权/校验） |
| DAO | 数据访问对象（§6.2） |
| view-model | 路由为模板格式化好的数据（§6.4） |
| 软删除/硬删除 | 标记删除 vs 物理删除 |
| 幂等 | 重复执行结果一致 |
| WAL | 预写日志（SQLite 并发模式） |
| 参数化查询 | 占位符绑值防注入 |
| 能力令牌 | 持 URL 即有权（§12.2） |
| CSP | 内容安全策略（script-src none） |
| 时序侧信道 | 靠比较耗时猜密钥的攻击（timingSafeEqual 防） |
| CSV 注入 | Excel 把 `=` 开头单元格当公式（csvCell 防） |
| 策略模式 | 接口 + 实现可替换（news 适配器） |
| 生产-消费 | 队列解耦（outbox） |
| 快照 vs 引用 | 稳定显示 vs 可控重算（单价表） |
| upsert | 存在则更新，不存在则插入 |
